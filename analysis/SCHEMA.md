# 分析輸出 schema

固定格式，這樣才存得起來、比得了。重跑同一筆許願時，靠 `模型版本` 與 `分析時間`
分辨是哪一版的判斷。

## 欄位對應（Notion「🌠 許願列表」）

| Notion 屬性 | 型別 | 誰填 | 說明 |
|---|---|---|---|
| `許願標題` | title | GAS 先填痛點前 24 字，分析時換成一句話摘要 | 摘要要看得出「為誰解什麼」 |
| `編號` | unique id | Notion 自動 | `WISH-n` |
| `狀態` | select | GAS 填 `許願中`，分析改 `已評估` | 見狀態機 |
| `痛點` | text | GAS（許願者原文） | **分析時不改寫** |
| `想如何解決` | text | GAS（許願者原文） | **分析時不改寫** |
| `期望功能` | text | GAS（許願者原文） | **分析時不改寫** |
| `呈現效果` | text | GAS（許願者原文） | **分析時不改寫** |
| `可行性` | select | 分析 | `可行` / `需縮小範圍` / `不可行` |
| `可行性分數` | number | 分析 | 1–5，定義見 `PROMPT.md` |
| `技術難點` | text | 分析 | **不准留空** |
| `AI 建議` | text | 分析 | 建議做法，兩到四句 |
| `實行方式` | text | 分析 | 可執行的步驟，一行一步 |
| `建議砍掉的範圍` | text | 分析 | 「只做兩天先砍什麼」 |
| `開發進度` | number | 開發時人工 | 0–100 |
| `目前功能` | text | 開發時人工 | 已完成的功能清單 |
| `版本` | text | 開發時人工 | |
| `demo 連結` | url | 開發時人工 | |
| `repo` | url | 開發時人工 | |
| `許願時間` | date | GAS | |
| `分析時間` | date | 分析 | |
| `模型版本` | text | 分析 | 實際跑分析的模型 ID |
| `已寄完成信` | checkbox | 寄信後 | |
| `反饋內容` | text | 收到反饋後 | |
| `納入下一版` | checkbox | 人工 | |

> **email 不在這張表上。** 個資只留在 Google Sheet 的 `email` 欄，
> 因為這個 Notion 頁面是可以公開的。

## 狀態機

```
許願中 → 分析中 → 已評估 ┬→ 排程中 → 開發中 → 已完成 → 反饋中 → 迭代中
                        └→ 不做（必須寄婉拒信說明原因）
```

## JSON 中介格式

分析時先產生這個結構再寫回 Notion，方便比對與重跑：

```json
{
  "wishId": "WISH-0001",
  "notionPageId": "…",
  "title": "一句話摘要：為誰解什麼",
  "feasibility": "可行 | 需縮小範圍 | 不可行",
  "score": 4,
  "technicalRisks": "至少一項；真的沒有就寫『想不到難點』",
  "recommendation": "建議做法，兩到四句",
  "implementation": ["步驟一", "步驟二", "步驟三"],
  "cutScope": "只做兩天的話先砍掉什麼",
  "analyzedAt": "2026-08-02",
  "modelVersion": "claude-opus-5"
}
```
